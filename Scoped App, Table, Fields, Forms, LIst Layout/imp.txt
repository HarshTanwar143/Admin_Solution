 Each entry in a table is a record. Every record is identified by a unique
32-character GUID called sys_id.

○ System Tables: No prefix (e.g., incident, user).
○ Global Custom Tables: Prefixed with u_ (e.g., u_car_requests).
○ Scoped Custom Tables: Prefixed with Scope ID (e.g., x_acme_app_table).

2. Out-of-the-Box (OOB) Tables
OOB Tables are tables that come pre-installed with the ServiceNow platform. They contain
built-in business logic, fields, and workflows.
● Task (task): The parent table for all work-related processes.
● Configuration Item (cmdb_ci): The base table for the CMDB.
● User (sys_user): Stores employee/user details.
● Group (sys_user_group): Stores teams and queues.
● Location (cmn_location): Stores physical addresses/sites



Types of the tables:
Base table
core table
custome table
M2M table
database view


In ServiceNow, the **backend/API name** of a many-to-many (junction) table is typically:

```text
m2m_<table1>_<table2>
```

### Example

If you create a many-to-many relationship between:

* `incident`
* `change_request`

The junction table backend name could be:

```text
m2m_incident_change_request
```

The **table that stores the definition** of many-to-many relationships is:

```text
sys_m2m
```

**In short:**

* **Junction table backend name:** `m2m_<table1>_<table2>`
* **Many-to-many definition table:** `sys_m2m`

### 1. Extended Table (Inheritance)

**Simple Definition:**
A table that **inherits fields and behavior from a parent table**.

**Example:**

* Parent: `task`
* Child: `incident`

The **Incident** table automatically gets fields like:

* Number
* State
* Priority
* Assigned To

from the **Task** table.

**Backend/System Field:**

* `sys_class_name` → Stores which child table the record belongs to (e.g., `incident`, `problem`).

---

### 2. Referenced Table (Reference)

**Simple Definition:**
A field that **stores a reference (pointer) to a record in another table**. It does **not** inherit fields.

**Example:**
The **Caller** field on an Incident references the **User** table.

Instead of storing the user's name, it stores the user's **`sys_id`**.

```text
Incident
---------
Caller → Ramesh Sharma

↓

Actually stores:

Caller = 6816f79cc0a8016401c5a33be04be441 (sys_id)
```

**Backend/System Field Type:**

* Dictionary field type: `Reference`
* It stores the referenced record's `sys_id`.

### One-line memory trick

* **Extended Table** → **Inheritance ("is-a")** relationship.
* **Referenced Table** → **Pointer ("has-a")** relationship.


**There is no separate backend table name for a "Referenced Table."**

A **reference** is just a **field type** in the **`sys_dictionary`** table.

**In very short:**

* **Reference field type:** `Reference`
* **Defined in:** `sys_dictionary`
* **Stores:** `sys_id` of another table's record.

Best Practice for Administrators
AVOID Deleting in Production.
Best Practice: Deactivate or Archive Instead:
1. Deactivate: Uncheck the Active box on the table record.
2. Archive: Use the Archiving module to preserve historical data while removing it
from the active table.
3. Remove UI Access: Delete the associated Modules and Application Menu.



Why Global Scope uses u_
Purpose: The prefix u_ (for "User" or "Custom") is automatically added to the Name of
any new field or table created in the Global scope.
Significance: It serves as a visual indicator that the element is custom-created by the
customer/administrator.
How Scoped Applications Use App-Specific Prefix
Scoped Applications use a different, unique prefix based on the application's unique
scope name (e.g., x_acme_proj_mgmt_).
Benefit: This enforces data separation and prevents naming collisions.


 Schema Map
The Schema Map is a graphical tool to visualize relationships between tables.

● Access: System Definition → Tables → Select Table → "Show Schema Map" link.
● Blue Bars: The table extends or is extended by another (Inheritance).
● Red Bars: The table references or is referenced by another (Reference fields)

The Dictionary defines the details of every field (column) in every table.
● Backend Table: sys_dictionary.
● What it controls:
○ Data Type: String, Integer, Reference, Date/Time, Choice.
○ Max Length: Character limit (Default 40 for string).
○ Mandatory: Is data required?
○ Read-Only: Can users edit it?
○ Display: (True/False) Which field is shown when this record is referenced
elsewhere? (e.g., User table uses "Name" as the Display field).
○ There can only be one Display=True field per table.

### 1. Dependent Field

**What it is:**
One field's options depend on the value of another field.

**Example:**

**Category:** Laptop

**Subcategory:** Battery, Keyboard, Screen

If you change:

**Category:** Printer

Then **Subcategory** becomes:

* Ink
* Paper Jam
* Toner

👉 **Subcategory depends on Category.**

---

### 2. Reference Qualifier

**What it is:**
Filters which records appear in a **Reference** field.

**Example:**

**Assigned To** (Reference → User table)

Without Reference Qualifier:

* Rahul
* Priya
* Amit
* Ramesh (all users)

With Reference Qualifier:

* Condition: **Department = IT**

Now only:

* Rahul
* Priya

are shown.

👉 **Reference Qualifier filters the lookup records.**

### Easy trick

* **Dependent** → **Field depends on another field.**
* **Reference Qualifier** → **Reference lookup is filtered by a condition.**

13. Dictionary Override
When a table extends Task, it inherits the dictionary settings of the parent. 
Dictionary Overrideallows the child table to change those settings without 
affecting the parent or other children.
● Backend Table: sys_dictionary_override.

Parent table: Task

Priority field → Not Mandatory

Child table: Incident

You make Priority → Mandatory

Only Incident is affected.
Task, Problem, and other child tables remain unchanged.

# ⭐ List Layout (Important)

**Definition:** Controls **which columns appear** in a list.

**Path:**
`Right Click List Header → Configure → List Layout`

**Example:**

* Before: Number, State
* After: Number, State, Priority, Assigned To

➡️ All users will see it if customized.

**Path:**
