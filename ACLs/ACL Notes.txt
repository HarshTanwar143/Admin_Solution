Allow If — Access is granted only if the conditions (role/script/condition) evaluate true. If false, access is denied.

Example: Allow If role = branch_manager → only branch managers can read Branch records; everyone else is blocked.

Deny Unless — Access is denied by default, and only allowed if condition is true — but it's stricter: it overrides all other Allow ACLs on that table/field, even ones granted elsewhere.

Example: Deny Unless role = admin on the account_number field → no matter what other ACLs say, only admins can see/edit account_number. Even if another ACL says "Allow If role=branch_manager", it still gets blocked unless they're admin too.

Simple way to remember:

Allow If = adds an opening (permissive).
Deny Unless = adds a lock that only one specific key can open (restrictive, overrides everything else).


Types of ACLs (by Type field):

record – controls access to entire rows/records in a table. E.g., who can read/write Branch records.
field – controls access to a specific field only. E.g., only branch_manager can edit interest_rate field, even if others can see the record.
table (used in wildcard *) – applies to the whole table via *.read, *.write etc. as a fallback default.
ui_page, ui_action, client_callable script, REST endpoint, etc. – special ACL types securing non-table resources like UI pages, Client Callable Script Includes, or Scripted REST APIs.

## Table-Level ACL Examples (record type)

**1. Branch – Read**
Role: `branch_manager` | Operation: read | Data Condition: `Branch Manager = Me (dynamic)`
→ A branch manager can only read the branch record assigned to them.

**2. Transaction – Create**
Role: `teller` | Operation: create | Data Condition: `Branch = User's Branch (dynamic)`
→ Tellers can only create transactions for their own branch.

**3. Account – Delete**
Decision Type: `Deny Unless` | Role: `bank_admin` | Operation: delete
→ No one except bank_admin can delete any Account record, overriding all other Allow ACLs.

**4. Loan Application – Write**
Role: `loan_officer` | Operation: write | Data Condition: `Status = Pending`
→ Loan officers can edit loan applications only while status is "Pending" — once approved/rejected, it's locked.

**5. Customer – Read**
Role: `customer_support` | Operation: read | Data Condition: `Region = Agent's Region`
→ Support agents can view only customers from their assigned region.

---

## Field-Level ACLs

**1. Account.balance – Write**
Type: field | Role: `bank_admin` | Operation: write
→ Only admins can directly edit account balance (regular tellers can't manually change it).

**2. Transaction.amount – Write**
Decision Type: `Deny Unless` | Role: `senior_teller` | Data Condition: `amount > 100000`
→ High-value transactions can only be edited by senior tellers; overrides other write ACLs.

**3. Customer.aadhaar_number – Read**
Role: `compliance_officer` | Operation: read
→ Sensitive ID field visible only to compliance officers, hidden from everyone else viewing the Customer record.

**4. Branch.branch_manager – Write**
Role: `regional_head` | Operation: write
→ Only regional heads can reassign who the branch manager is (regular staff can't change it).

**5. Loan.interest_rate – Write**
Role: `loan_officer` | Operation: write | Data Condition: `Status = Draft`
→ Interest rate is editable only while the loan is in Draft status; locked after submission.

SUMMARY :
Yes, that's correct! Example:

**Role**: `senior_teller` | **Operation**: write | **Data Condition**: `amount > 100000`
→ Only senior tellers can edit transaction records where amount exceeds 1,00,000.

**Yes**, these 3 are the core things to think about for any ACL:
1. **Role** – *who* is allowed
2. **Operation** – *what action* (read/write/create/delete)
3. **Data Condition** – *on which records* (based on field values)

A couple more to keep in mind alongside these (less frequently, but still important):
- **Type** – record or field level
- **Decision Type** – Allow If vs Deny Unless (especially when you want to override other ACLs)

But for 90% of practical scenarios, **Role + Operation + Data Condition** is exactly the right way to think about it.

**1. Table Level ACL**
Type: `*` (wildcard) | Table: Transaction | Operation: read
→ Controls default read access for the **entire Transaction table**, applies to 
all records unless overridden.

**2. Record Level ACL**
Type: record | Table: Branch | Operation: write | Role: `branch_manager` | 
Data Condition: `Branch Manager = Me`
→ Branch manager can edit only their own branch record.

**3. Field Level ACL**
Type: field | Table: Account | Field: `balance` | Operation: write | Role: `
bank_admin`
→ Only admin can edit the `balance` field, even if others can edit the rest of 
the record.

**4. List Edit ACL**
Type: field | Table: Loan | Field: `interest_rate` | Operation: `list_edit` | 
Role: `loan_officer`
→ Controls whether `interest_rate` can be **inline-edited directly from the list
view** (not the form) — even if form-edit is allowed, list_edit can be blocked 
separately.

Admin overrides:
If checked ✅, users with the admin role automatically bypass this ACL — no need 
to satisfy role/data condition.

Example: Your ACL says "only branch_manager can edit Branch records." If Admin 
Overrides is checked, an admin user can still edit any Branch record even without 
the branch_manager role.
If unchecked ❌, even admins must satisfy the ACL's conditions like everyone 
else.

Protection policy:
Controls whether this ACL record itself can be edited/deleted by others later — it's
 about protecting the ACL configuration, not the data.
Example: You set Protection Policy = "Protected" on your critical Account.balance 
write ACL. Now, no one (even devs) can accidentally delete or modify that ACL 
record without special permission — keeps your security rule safe from being 
tampered with.
