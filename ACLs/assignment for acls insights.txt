they can only read only the ids?Correct interpretation: All Unique ID fields (Project ID, Assignment ID, Skill ID, Skill Mapping ID) should be read-only for everyone except Operations — they can view the ID but not edit it.
How to do it (Field-level ACLs):
For each ID field on each table, create a field-level write ACL:
Example (Project ID field):

Type: field
Table: Project | Field: Project ID (number/unique field)
Operation: write
Decision Type: Deny Unless
Requires role: technova.operations




if i applied ui policy as read only on project id and in acl i give permission to write it means to modify it to operation user so will it modify it? in very short

No — UI Policy wins visually, but even if you remove the UI Policy, ACL alone still can't make an auto-number field editable.

Auto-number fields (like Project ID) are inherently read-only in the form UI by ServiceNow's core field-type behavior — this isn't controlled by ACL or UI Policy at all. Even if:

ACL allows write for Operations, and
No UI Policy makes it read-only,
...the field will still appear grayed out because that's how Auto Number field type behaves natively in ServiceNow.

In short: ACL/UI Policy control security/visibility layers, but the field type itself (Auto Number) overrides and stays uneditable regardless.

Since your record-level `write` ACL likely only allows the `operations` role (based on earlier steps), Developer **fails at the record level itself** — so it doesn't even matter that Developer passes the field-level Comments ACL. Record-level check blocks him first.

**Fix:** Add `developer` role to the **record-level write ACL** too (not just the field-level one) — so Developer passes both checks:
1. Record-level write ACL ✅ (needs developer added)
2. Field-level write ACL on Comments ✅ (already has developer)

**In short:** You gave developer field-level write, but forgot to also give them record-level write — both are required together.


Yes — Developer needs **record-level write** access on the table (at least basic write permission), otherwise field-level ACLs never even get checked.

**But careful:** Giving record-level write opens **all fields** by default, unless you **also lock down other sensitive fields individually** with their own field-level ACLs (like you did for ID fields with Deny Unless).

**Pattern to remember:**
- Record-level write ACL = "can this role edit records at all?" (broad gate)
- Field-level ACL = "can this role edit *this specific field*?" (fine-tune within that gate)

So yes, **every time** you want a role to edit *any* field via field-level ACL, that role must first pass the record-level write ACL too — it's not one-time, it's just how the security layering works.
